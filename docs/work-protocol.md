# Рабочий протокол: как задачи доводятся до конца

Действует для меня (root-агент) и для любого субагента/воркера, которому отдаётся работа по проекту. Цель — **ноль невыполненных задач**: каждая строка отзыва заканчивается либо «сделано + доказательство», либо «вопрос владельцу» с явно названным блокером и тем, что именно от него нужно.

## 1. Разбор (до любых правок)
1. Прочитать файл отзывов целиком, выписать **каждый id** (24 строки — 24 id, не «примерно»).
2. Для каждого id определить тип: `баг` / `улучшение` / `вопрос` / `маркер-ложняк` / `старая сборка`.
3. Проверить по коду текущее состояние: `сделано` / `не сделано` / `частично` — с указанием файла и строки. Догадки запрещены: только прочитанный код.
4. Свести в таблицу: id → действие → файлы → критерий приёмки (что должно измениться и каким тестом проверяется).
5. Дубли и вопросы явно помечать: вопрос не «исправляется», на него даётся ответ (в приложении или в доке) + фиксируется в журнале.

## 2. Назначение работы
- Один воркер = один непересекающийся набор файлов. Пересечение файлов между воркерами запрещено: иначе чужие правки затираются.
- В задании воркеру обязательно: список разрешённых файлов, запрет трогать `sql/`, `windows/`, `build/`, `.claudeignore`, `SUPABASE-CREATE.md`, `TASK-sync-mapping.md`, запрет коммитов и пушей, требование `flutter analyze --no-fatal-infos`, формат ответа (что изменено, анализ, тесты, `git diff --stat`), список того, что нельзя выдумывать (данные, API, ключи).
- Работа идёт волнами: сначала критичный баг, потом UI-пакеты, потом сервисы; внутри волны — параллельно, но только при непересекающихся файлах.

## 3. Приёмка работы воркера (нельзя «поверить на слово»)
1. Открыть `git diff` по каждому файлу и прочитать все хунки (не только `--stat`).
2. Проверить: нет ли ошибок компиляции, не сломаны ли смежные вызовы, не удалены ли чужие функции, не появились ли «заглушки».
3. Сверить каждый пункт задания с реальным диффом; несовпавший пункт — вернуть воркеру или доделать самому **до** коммита.
4. Если воркер упал по инфраструктуре (сеть, лимит ходов) — сначала `git status` и `flutter analyze`: работа могла остаться недоделанной; доделать руками, а не перезапускать вслепую.

## 4. Гейты перед коммитом (все обязательны)
- G1 `flutter analyze --no-fatal-infos` → **0 errors, 0 warnings** (info допустимы).
- G2 целевые тесты по изменённым модулям.
- G3 полный `flutter test` → все зелёные, число тестов не меньше предыдущего прогона.
- G4 новые тесты на новую логику: чистая функция — unit-тест; новый виджет — хотя бы smoke без переполнений на 360×640 и 1280×800.
- G5 обновлён журнал `docs/feedback-YYYY-MM-DD.md`: строка на каждый id с итогом.

## 5. Финальная проверка (после всех правок, до отчёта)
1. Прогнать G1–G3 ещё раз на чистом дереве.
2. Составить отчёт по **всем** id: `сделано` / `нужна проверка на устройстве` / `вопрос` / `ждёт действия владельца` — без пустых строк и без «в процессе».
3. Проверить CI после пуша (Pages, APK, переводы). Если статус недоступен (нет токена) — написать это прямо в отчёте и указать, что именно не подтверждено, а не молчать.
4. Проверить, что в репозитории нет недоделанных файлов: `git status` чистый, кроме известных чужих (`sql/`, `windows/generated_*`, служебные файлы другого ИИ).
5. Обновить память: принятые решения и то, что требует ручного действия владельца (например, SQL-миграция).

## 6. Стоп-правила
- Нельзя заканчивать ход с компиляционной ошибкой или красным тестом.
- Нельзя писать «сделано», если нет ни теста, ни проверки анализа.
- Нельзя оставлять пункт «в плане» без владельца: у каждого незакрытого пункта должен быть либо срок/шаг, либо явный вопрос.
- Нельзя отправлять пользователю отчёт без итоговой проверки — проверка обязательна.

## 7. Чек-лист отчёта
- [ ] все id из файла отзывов упомянуты;
- [ ] по каждому — статус и доказательство (файл/тест/лог);
- [ ] незакрытые — с причиной и тем, что нужно от владельца;
- [ ] анализ и тесты приведены цифрами;
- [ ] CI или явное «не подтверждено, потому что …».
