# Медиа чата через R2 (фото/файлы), с шифрованием

Решение пользователя 18.11.2026: **P2P первым, R2 — постоянное хранилище и
запасной путь**, шифрование обязательно, лимиты пользователю не показываем.

## Как устроено

```
телефон A ──(P2P DataChannel, если канал есть)──► телефон B
      │
      └─(если P2P нет/собеседник офлайн)─► шифрование AES-256-GCM ─► воркер ─► R2 (nexusbox)
                                                                    │
телефон B ◄──(ссылка-идентификатор в сообщении)── воркер ──────────┘
```

- В сообщении чата лежит только 32-символьный идентификатор объекта
  (128 случайных бит) — не адрес и не сам файл.
- Файл шифруется на устройстве: X25519 (своя пара ключей у каждого),
  общий секрет → HKDF-SHA256 → AES-256-GCM. Открытый ключ публикуется в
  переписке служебным сообщением `NX1:pk:<base64>`, приватный не покидает
  устройство. Поэтому в R2 лежит шифротекст, а в базе чата — только
  идентификатор: ни Cloudflare, ни Postgres открытый файл не видят.
- Ключи пользователя хранятся в локальной базе (`color_prefs`,
  `media_x25519_priv`), как тема оформления.

## Пределы (проверяет воркер, пользователь их не видит)

| Что | Значение | Где задаётся |
|---|---|---|
| Потолок бакета | 8 ГБ из бесплатных 10 ГБ | `MEDIA_LIMIT_GB` |
| На пользователя в месяц | 1 ГБ | `MEDIA_USER_LIMIT_MB` |
| Один файл | 25 МБ | `MEDIA_MAX_OBJECT_MB` |

При превышении сервер отвечает `413`; клиент **молча** отправляет файл старым
путём (через базу) — для человека это просто «чуть медленнее». Никаких
сообщений о лимитах в интерфейсе нет.

Эндпоинты воркера: `POST /media/upload`, `GET /media/<key>`, `GET /media/usage`
(последний — только для диагностики разработчика).
